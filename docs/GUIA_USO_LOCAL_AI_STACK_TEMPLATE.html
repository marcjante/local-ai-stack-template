1. ¿Qué es Local AI Stack Template?

Local AI Stack Template es una plantilla genérica para construir aplicaciones de IA locales, reproducibles y organizadas por proyectos. La intención es poder reutilizar la misma infraestructura para distintos casos de uso sin tener que volver a crear desde cero el backend, la base de datos, los workers, la gestión de tareas, los plugins o el sistema de auditoría.

Qué resuelve

  • Separación de datos por proyecto.
  • Ejecución asíncrona mediante colas.
  • Plugins reutilizables.
  • Persistencia en PostgreSQL.
  • Integración con RAG y documentos.
  • Auditoría y trazabilidad.
  • Migraciones reproducibles.
  • Pruebas automatizadas y CI.

Ejemplo incluido

El proyecto incluye como caso funcional completo un módulo de revisión sistemática con: protocolo, estrategias de búsqueda, PubMed, cribado por IA, decisiones humanas, conflictos, texto completo, extracción de datos y trazabilidad.

Estado actual: instalación limpia validada sobre PostgreSQL vacío, migraciones Alembic completas y suite de pruebas con 89 tests superados.

4. Requisitos

Python

Python 3.9+ local. CI validado con Python 3.11.

PostgreSQL

Base de datos principal. CI validado con PostgreSQL 16.

Redis

Broker para RQ y workers asíncronos.

También se recomienda tener instalados Git, GitHub CLI y un entorno virtual de Python.

5. Instalación desde cero

5.1 Clonar el repositorio

git clone https://github.com/marcjante/local-ai-stack-template.git
cd local-ai-stack-template

5.2 Crear el entorno virtual

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements-dev.txt

5.3 Preparar variables de entorno

cp .env.example .env

Edita .env y adapta la conexión PostgreSQL a tu sistema.

DATABASE_URL="dbname=stack_template user=TU_USUARIO host=127.0.0.1 port=5432"
No uses literalmente TU_USUARIO. Debe ser sustituido por el usuario PostgreSQL real de la máquina.

5.4 Crear la base de datos

createdb stack_template

5.5 Ejecutar todas las migraciones

alembic -c alembic.ini upgrade head

La instalación debe recorrer toda la cadena de migraciones hasta el head actual sin errores.

7. Arranque del sistema

El stack requiere normalmente tres elementos en ejecución:

  1. PostgreSQL.
  2. Redis.
  3. Backend/dashboard y los workers necesarios.

Comprobaciones básicas

psql -d stack_template -c "SELECT current_database();"
redis-cli ping

Redis debe responder:

PONG
Los comandos concretos de arranque del dashboard, backend y workers dependen de la configuración declarada en config/services.yaml. El panel también dispone de controles y diagnóstico de servicios.

8. Gestión multiproyecto

La arquitectura está diseñada para que distintos proyectos compartan infraestructura pero no mezclen sus datos. Las operaciones sensibles se filtran mediante project_id.

ConceptoRegla
Proyecto activoDetermina el ámbito del dashboard.
TareasSe almacenan con project_id.
Revisiones sistemáticasSiempre asociadas a un proyecto.
CribadoEl artículo y la revisión deben pertenecer al proyecto activo.
ExtracciónLa validación humana y la IA quedan restringidas por proyecto.
AuditoríaLos eventos incluyen project_id y review_id.
Nunca elimines los filtros por project_id en consultas sensibles: son una barrera esencial contra contaminación de datos entre proyectos.

9.1 Protocolo

Define el objetivo, criterios de inclusión/exclusión y estructura metodológica. Los cambios relevantes pueden quedar registrados en review_audit_log.

9.2 Estrategias de búsqueda

Las estrategias están versionadas por revisión y base de datos. Existe protección tanto en la aplicación como en la base de datos frente a versiones duplicadas.

9.3 PubMed

El plugin de PubMed puede ejecutar búsquedas y guardar resultados dentro de la revisión correspondiente. Las operaciones de persistencia validan el proyecto antes de insertar resultados.

9.4 Cribado por IA y humano

El cribado automatizado propone decisiones. Los revisores humanos pueden registrar decisiones independientes. El consenso automático solo se produce cuando todas las decisiones registradas coinciden.

Si existe desacuerdo entre revisores, se abre o reabre un conflicto. No se aplica una mayoría simple de forma silenciosa.

9.5 Texto completo

Los documentos a texto completo pueden recuperarse o cargarse manualmente. La carga valida revisión, artículo, fase, duplicados y proyecto, y puede indexar el contenido en el sistema RAG.

9.6 Extracción de datos

Los campos de extracción se definen por revisión. La IA puede proponer valores y un revisor humano puede validarlos posteriormente. Ambos caminos se auditan.

10. Workers, colas y plugins

Las tareas pesadas no tienen que ejecutarse dentro de la petición HTTP. El backend crea una tarea, la persiste y la coloca en una cola RQ. Un worker recoge esa tarea y llama al plugin correspondiente.

Flujo

HTTP/API
  ↓
create_task(...)
  ↓
PostgreSQL: tasks
  ↓
Redis / RQ
  ↓
worker
  ↓
plugin.handle(task_id, payload)
  ↓
resultado + auditoría

El cargador de plugins descubre módulos que exponen, como mínimo, un nombre de cola y una función handle(task_id, payload).

11. Documentos y RAG

El modelo de datos incluye:

  • collections: agrupaciones lógicas por proyecto.
  • documents: documentos registrados.
  • rag_chunks: fragmentos indexables.

Los fragmentos pueden almacenar metadatos como número de página, sección, offsets y metadatos adicionales según las migraciones activas.

Regla de diseño: cuando un esquema evoluciona, los cambios nuevos deben introducirse mediante una migración Alembic, no incorporándose retroactivamente a la baseline.

12. PostgreSQL y Alembic

12.1 Regla principal

Una vez publicada una migración, debe considerarse histórica. La baseline utiliza ahora db/migrations/baseline_schema.sql, un snapshot congelado del esquema núcleo original.

12.2 Crear un cambio de esquema nuevo

alembic revision -m "describe el cambio"

Edita el nuevo archivo de migración y después:

alembic -c alembic.ini upgrade head

12.3 Ver la versión actual

alembic -c alembic.ini current

12.4 Probar una instalación limpia

dropdb --if-exists stack_template_ci_test
createdb stack_template_ci_test

DATABASE_URL="dbname=stack_template_ci_test user=TU_USUARIO host=127.0.0.1 port=5432" \
alembic -c alembic.ini upgrade head

dropdb stack_template_ci_test

13. Backup y restauración

El sistema de backup incluye información de la base de datos y recursos asociados. La restauración de PostgreSQL está configurada para detenerse ante errores y ejecutarse dentro de una transacción.

La extracción de archivos ZIP está protegida frente a rutas de tipo path traversal.

Una restauración es una operación de alto impacto. Debe probarse primero sobre una base temporal antes de utilizarla sobre datos importantes.

16. Cómo crear un nuevo plugin

Un nuevo plugin debe vivir dentro de workers/plugins/.

Plantilla conceptual

QUEUE_NAME = "mi_cola"

def handle(task_id, payload):
    project_id = payload.get("project_id")
    if not project_id:
        raise ValueError("project_id es obligatorio")

    # 1. Validar payload
    # 2. Validar ámbito del proyecto
    # 3. Ejecutar trabajo
    # 4. Guardar resultado
    # 5. Registrar auditoría si corresponde

    return {"status": "ok"}
Para plugins que acceden a información de proyecto, no aceptes implícitamente datos de otro proyecto. Valida siempre project_id antes de leer o modificar datos.

17. Cómo reutilizar la plantilla para otro proyecto

La intención no es convertir todo en una revisión sistemática. Ese módulo es un caso de uso construido encima de una infraestructura genérica.

Proceso recomendado

  1. Crear el proyecto desde el panel.
  2. Definir qué datos son propios del nuevo dominio.
  3. Crear nuevas tablas mediante Alembic si hace falta.
  4. Crear plugins para las tareas de procesamiento.
  5. Registrar nuevas colas y herramientas.
  6. Añadir vistas o endpoints específicos.
  7. Asegurar que todas las consultas se filtran por project_id.
  8. Añadir tests antes de integrar en main.

Ejemplos de reutilización:

Revisión científica
Búsqueda, cribado, extracción.
Chatbot clínico
RAG, documentos, evaluación y seguridad.
Procesamiento documental
Ingesta, análisis y generación de resultados.

18. Seguridad y aislamiento

  • El dashboard está pensado para uso local y debe mantenerse ligado a 127.0.0.1.
  • Los secretos deben permanecer en .env, nunca en Git.
  • Los datos deben filtrarse por proyecto.
  • Los archivos comprimidos se validan antes de extraerse.
  • Las restauraciones de PostgreSQL deben fallar de forma explícita ante errores.
  • Los cambios de esquema deben pasar por Alembic.
No expongas directamente el dashboard de administración a Internet sin añadir una capa de autenticación, autorización, HTTPS y endurecimiento específico.

20. Problemas frecuentes

zsh: command not found: alembic

Normalmente significa que el entorno virtual no está activo.

source .venv/bin/activate
which alembic

role "postgres" does not exist

La URL de conexión usa un usuario PostgreSQL que no existe en la máquina.

psql -c "\du"

DuplicateColumn durante una instalación limpia

Suele indicar que una columna nueva se incluyó por error en la baseline y también en una migración posterior. La baseline debe representar solamente el esquema histórico original.

UndefinedTable durante baseline

Significa que la baseline está intentando crear una tabla con una FK hacia otra tabla que todavía no existe. No debe solucionarse ocultando el error: hay que revisar el orden histórico de las migraciones.

GitHub Actions falla pero local funciona

Reproduce una base completamente vacía. Una base local antigua puede contener tablas o columnas que oculten errores de migración.

21. Flujo recomendado para publicar una release

  1. Comprobar estado Git.
  2. Ejecutar migraciones sobre una DB limpia.
  3. Ejecutar la suite completa.
  4. Commit.
  5. Push a main.
  6. Esperar CI verde.
  7. Crear tag.
  8. Publicar release en GitHub.
git status
pytest tests/ -v
git add .
git commit -m "Descripción del cambio"
git push origin main

gh run list --workflow=tests.yml --limit 3

Para correcciones posteriores a una versión publicada, es preferible crear una versión de parche como v1.0.1 en lugar de reescribir silenciosamente el tag anterior.
